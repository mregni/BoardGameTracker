The rules assistant lets you ask natural-language questions about a game's uploaded rulebook(s) — for example *"how many cards do you start with?"* — and get an answer with page citations. Answers are grounded in the manuals you uploaded: the assistant only uses their content.

It runs **fully locally** by default through [Ollama](https://ollama.com/), so your rulebooks and questions never leave your server. No API keys and no cloud services are required.

<Aside type="caution">
The rules assistant is **disabled by default** and needs enough hardware to run a local language model. On a low-powered server (for example a Raspberry Pi or a small NAS), leave it disabled.
</Aside>

## Enabling it

The [quick-start stack](/BoardGameTracker/getting-started/quick-start/) doesn't include the AI service. To turn the assistant on, add an `ollama` service to your `docker-compose.yml` and point the app at it:

```yaml title="docker-compose.yml (additions)"
services:
  boardgametracker:
    environment:
      # ...your existing values...
      - RAG_ENABLED=true
      - AI_BASE_URL=http://ollama:11434
      - AI_CHAT_MODEL=qwen3:4b

  ollama:
    image: ollama/ollama:latest
    restart: unless-stopped
    volumes:
      - ./ollama:/root/.ollama
```

Then (re)start the stack:

```bash
docker compose up -d
```

The required models (`bge-m3` for search, plus your `AI_CHAT_MODEL`) are pulled **automatically when the container starts**, and re-checked on every restart — no manual `ollama pull` needed. Changing the chat model later just needs a redeploy.

Once enabled, every uploaded manual is indexed automatically in the background. Manuals uploaded before enabling are indexed on the next start.

## Models

| Role | Model | Where it runs |
| --- | --- | --- |
| Embeddings (search) | `bge-m3` (fixed) | Always **local Ollama**. Chosen for multilingual rulebooks (English, Dutch, French, German, …). |
| Chat (answers) | `qwen3:4b` by default | Local Ollama **or** a hosted provider — set `AI_CHAT_MODEL` / `AI_PROVIDER`. |

The embedding model is fixed at `bge-m3` (1024 dimensions) so the vector search stays consistent with what's already stored in the database — it always runs locally. The **chat** model is independent: run it locally, or point it at a hosted provider (see [below](#using-a-hosted-chat-model)) while embeddings stay on your server.

## Which chat model should I use?

Larger models give better answers but need more memory, and ideally a GPU. Set your choice with `AI_CHAT_MODEL`.

| Your hardware | Suggested `AI_CHAT_MODEL` |
| --- | --- |
| Raspberry Pi / under 8 GB RAM | Not recommended — keep the assistant disabled. |
| ~8 GB RAM, CPU only | `qwen3:4b` (default) or `mistral:7b` |
| 16 GB RAM, or a 6–8 GB GPU | `qwen3:8b` |
| 12–16 GB GPU | `qwen3:14b`, `gemma3:12b`, or `qwen3:30b-a3b` |
| 24 GB+ GPU | `command-r` |

The `bge-m3` embedding model runs fine on CPU across the board.

## GPU acceleration (NVIDIA)

By default Ollama runs on the CPU. To use an NVIDIA GPU for much faster answers:

1. Install the [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html) on the host.
2. Start the bundled **`docker-compose.gpu.yml`** — a complete, ready-to-run stack with the assistant enabled and the GPU reserved for Ollama:

   ```bash
   docker compose -f docker-compose.gpu.yml up -d
   ```

The full file:

```yaml
services:
  boardgametracker:
    image: uping/boardgametracker:latest
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./images:/app/images
      - ./logs:/app/logs
      - ./manuals:/app/manuals
    ports:
      - "5444:5444"
    environment:
      - DB_HOST=db
      - DB_USER=dbuser
      - DB_PASSWORD=CHANGEME
      - DB_NAME=boardgametracker
      - DB_PORT=5432
      - JWT_SECRET=CHANGEME_GENERATE_AT_LEAST_32_CHARACTERS
      - TZ=UTC
      - RAG_ENABLED=true
      - AI_BASE_URL=http://ollama:11434
      - AI_CHAT_MODEL=qwen3:8b
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5444/api/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s

  db:
    image: pgvector/pgvector:pg16
    restart: unless-stopped
    volumes:
      - ./postgres-data:/var/lib/postgresql/data
    environment:
      - POSTGRES_DB=boardgametracker
      - POSTGRES_USER=dbuser
      - POSTGRES_PASSWORD=CHANGEME
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U dbuser -d boardgametracker"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 10s

  ollama:
    image: ollama/ollama:latest
    restart: unless-stopped
    volumes:
      - ./ollama:/root/.ollama
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
```

A 6 GB card such as a GTX 1060 can run `qwen3:8b`, but not while the embedder is also on the GPU: the chat model needs roughly 5.5 GB and `bge-m3` another ~0.6 GB, so the two don't both fit in 6 GB. Pin the embedder to the CPU (see below) and the chat model gets the whole card.

### Small GPUs: keep the embedder off the card

On a tight GPU (around 4 GB) a local chat model and the `bge-m3` embedder compete for memory. When they don't both fit, Ollama offloads part of the chat model to the CPU and generation slows to a crawl. Because the embedder is small and only handles one short query per question, the fix is to **pin it to the CPU** so the chat model keeps the whole GPU:

```yaml
    environment:
      - AI_EMBEDDING_NUM_GPU=0   # run bge-m3 on CPU
```

With this set, the chat model stays resident on the GPU across questions — only the first answer after startup pays the load time. The default (`-1`) lets Ollama decide, which is right when the GPU has room to spare (a bigger card, or a hosted chat model that leaves the GPU free).

## Rulebook page images

Each answer's citations include a thumbnail of the actual rulebook page they were drawn from, so you can check the source at a glance. Pages are rendered on the server on demand and cached — no configuration is needed, as the container ships with the renderer (`poppler-utils`) built in. If the renderer is ever unavailable, answers simply fall back to text-only citations.

## Using a hosted chat model

You can keep embeddings local while sending the **chat** step to a hosted, OpenAI-compatible provider — a good option if you want stronger answers than your hardware can run locally. Only the chat model is hosted; `bge-m3` embeddings and the vector search always stay on your server.

**OpenAI (ChatGPT):**

```yaml
    environment:
      - AI_PROVIDER=openai
      - AI_BASE_URL=https://api.openai.com/v1
      - AI_CHAT_MODEL=gpt-4o-mini
      - AI_API_KEY=sk-...
```

**Claude (Anthropic)** — through its OpenAI-compatible endpoint:

```yaml
    environment:
      - AI_PROVIDER=openai
      - AI_BASE_URL=https://api.anthropic.com/v1
      - AI_CHAT_MODEL=claude-sonnet-4
      - AI_API_KEY=sk-ant-...
```

You still need the local Ollama service for embeddings (it only has to run `bge-m3`, which is small). With a hosted chat model the GPU is used for embeddings alone, or you can skip a GPU entirely.

<Aside type="caution">
Only the current question and the rulebook excerpts retrieved for it are sent to the hosted provider. Your full rulebooks are not uploaded, but those excerpts do leave your server — keep that in mind for private material.
</Aside>

<Aside type="note">
Changing `AI_CHAT_MODEL` takes effect after a redeploy: the container pulls any missing local model on startup, so no manual `ollama pull` is needed. The database (`pgvector/pgvector:pg16`) image is required whether or not the assistant is enabled.
</Aside>
